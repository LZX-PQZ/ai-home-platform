## 请 D 确认的最小只读协议

建议 `GET /api/provider/orders`，不接受客户端指定当前身份的 providerId。以下为提案，当前页面不会请求此路径。

| 建议公共 OrderSummary 字段 | 类型、必填性、含义 |
|---|---|
| id | 必填 Id，服务端生成的接单关系编号 |
| demandId | 必填 Id，关联需求 |
| providerId | 必填 Id，须与服务端已认证身份一致 |
| acceptedQuoteId | 必填 Id，已被接受且属于同一需求、服务方的报价 |
| status | 必填，建议 contracted / in_progress / completed；由 D 确认与 Demand.status 的对应、是否按服务方独立流转，客户端不推导或修改 |

成功返回公共 `envelope(OrderSummary[])`，保持 mock/live 来源。首次可仅展示关联编号和状态；若需要城市、预算或工期，请由 D 复用已有公共 Demand/Quote 字段并明确可查看范围，不让 C 另造 DTO 或把期望工期视为实际工期。未知费用继续为 null。

示例（仅待确认的协议，非当前订单或真实业务结果）：

```json
{
  "ok": true,
  "data": [
    { "id": "example-order", "demandId": "example-demand", "providerId": "example-provider", "acceptedQuoteId": "example-quote", "status": "contracted" }
```

## 身份、状态与失败规则

- 身份来自服务端认证，角色导航不是身份来源；未认证 401，无服务方权限 403。演示模式如需固定身份，应有明确的服务端规则与 mock 标识，不能允许客户端任选 providerId 冒充本人。
- 经授权且没有接单时返回成功空数组；网络失败、权限问题、501/503 不得转换为成功空数组或返回默认演示订单。
- 所有失败复用 ApiFailure；接口尚未实现为 501，存储不可用为 503。分页、排序及总数如需要，由 D 先定义，C 不猜测查询参数。
- 请明确接单关系的生成时机、同一需求多个服务方的归属、报价接受与接单创建的一致性，以及取消/拒绝是否需要新增状态。既有未签约需求和旧 mock 不自动变成接单记录。

## 交接验收

1. 两个服务方分别只能读取自己的接单；伪造身份参数不能扩大权限。
2. submitted 报价、其他服务方报价、未签约需求不会出现在当前服务方列表；每条接单能追溯同一需求及 accepted 报价。
3. 空列表、401/403、501、503 和刷新后的状态变化可区分，错误不会保留旧记录冒充最新结果。
4. 数据来源明确，mock 不表示真实履约；状态和金额均按公共契约校验。
