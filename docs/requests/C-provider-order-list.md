# C：本人接单列表接入

基于 main `fd334dd`，接入 D 已合并的 PR #119（`D-quote-acceptance.md`）。本次仅完成 `/provider/orders` 的只读接单关系展示，沿用原本人报价与明细。

## 行为与验收口径

- 固定无参数 `GET /api/provider/orders`，通过共享 apiGet 与公共 OrderSummary.array() 校验，身份由服务端确定。不根据 accepted 报价猜测或补造接单。
- 展示接单、需求、已接受报价、服务方编号与 contracted/in_progress/completed 状态；编号顺序沿用返回结果，不称成交时间顺序。单需求/单报价对应一条关系，重复关联拒绝整份列表。
- 列表 meta.source 与逐条 source 独立展示。当前演示服务方认证使列表整体为 mock，实际数据库保存不升级来源、不表示生产认证。未返回费用、工期、合同、付款或验收信息，不补猜。
- 合法空列表明确暂无接单。401/403 引导服务方登录，501 不视为成功，503/网络/坏数据不冒充空列表；刷新先清除旧记录，加载中禁用按钮。
- 接单与报价各自读取和刷新，页面说明登录/退出/身份变化后分别刷新。需求签约后服务方不能凭接单关系读取私有需求，暂仅展示关联编号，报价沿用现有授权查询与明细。

## 共享交接与剩余事项

无公共契约、API、依赖、配置或鉴权变更。B 的业主接受报价页面仍由 B 接入；C 不提供代业主接受、取消/改选、付款、开工、验收或状态推进。管理员全量访问、生产服务方认证及共享登录事件自动刷新仍未交付。

后续请求 D：在现有需求详情读取协议中明确已签约服务方的可见字段及访问规则，再由 C 接入详情。当前 published 公开、非 published 仅所属业主可读，因此本轮不绕过权限、不自行扩权。

- 建议继续使用 `GET /api/demand/[id]` 与公共 `Demand` 字段，不新增客户端身份字段或查询参数，也不返回业主账号/凭证等私有信息；字段均沿用现有类型与必填性。
- 请 D 评估在事务内验证当前服务方会话、绑定、同需求 ServiceOrder/accepted 报价一致性后，允许读取本人 contracted/in_progress/completed 需求。无本人关系与不存在需求统一拒绝，失效凭证不得降级公开读取，保留已定义的双会话优先级与来源规则。
