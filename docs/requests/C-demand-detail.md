# C → D：服务方需求详情查询

- 申请角色：C
- D 处理状态：待讨论。
- 用户场景：从需求大厅点击一条已发布需求，或直接打开 `/provider/demand/[id]`，查看对应记录；不能用 `demo-demand` 冒充其他 ID。

## C 本次独立完成的部分

- 沿用现有详情页面路径，不新增 API。通过公共 `apiGet` 读取 `GET /api/demand`，以 `Demand.array()` 校验后，在已发布记录中按 ID 精确查找。
- 页面明确说明详情取自当前列表，展示接口的 `meta.source`；模拟数据不冒充真实需求。
- 找不到只提示“当前列表中未找到该已发布需求”，不声称后台资源不存在，也不回退到其他需求。列表分页、过滤或发布状态变化均可能导致记录不在列表中。
- 只读详情、加载、错误、重试及返回大厅已实现；不提供写入、报价提交或接单。角色导航和客户端筛选不是鉴权。

## 需要 D 提供

1. 新增 `GET /api/demand/[id]`，以公共 `envelope(Demand)` 返回单条需求，响应的 `data.id` 必须等于路径中的 ID。
2. 继续复用现有 Demand 字段，不申请新增业务字段或复制 DTO。id 为非空字符串；城市、描述、状态、改造类型、面积、预算上下限和期望天数仍按现有契约，金额单位为人民币分。
3. 服务端确认服务方可查看范围并实施鉴权和数据隔离；未经授权不得返回草稿或其他私有记录。当前 C 页面仅展示已发布需求，后续已接单需求访问范围请单独明确。
4. 非法 ID 返回 400；不存在或不可查看的资源返回 404（不泄露私有资源是否存在）；未实现时为 501。错误均使用公共 `ApiFailure`，不得返回 HTTP 200 的默认演示需求作为成功兜底。
5. 更新 `docs/API.md`，补充单条查询、来源和授权规则；按需要调整 D 所有的 API、数据访问、mock 及测试。与 `docs/requests/B-demand-query.md` 的需求可一起协调。

## 请求与响应示例

`GET /api/demand/demo-demand`（固定演示来源）

```json
{
  "ok": true,
  "data": {
    "id": "demo-demand",
    "description": "演示需求：浴室防滑改造",
    "city": "深圳",
    "areaM2": 60,
    "budgetMinCents": 3000000,
    "budgetMaxCents": 5000000,
    "renovationType": "elderly",
    "desiredDays": 30,
    "status": "published"
  },
  "meta": { "source": "mock" }
}
```

404 示例：

```json
{"ok": false, "error": {"code": "DEMAND_NOT_FOUND", "message": "需求不存在或不可查看"}}
```

## 兼容与交接验收

- 保持现有列表接口与 Demand 契约兼容；详情接口作为新增能力，避免影响 A/B 的调用方。
- D 的接口合并后，C 再将 `src/features/c/demand-detail.ts` 切换到单条查询，撤下列表查询限制说明；本次不会预先调用不存在的接口。
- 使用两个不同 ID 的已发布需求验证各自内容；未知 ID、未授权和草稿不返回默认记录。
- 模拟数据保留 mock，接通真实数据后才标 live。网络失败、无效响应和 501 都显示错误，不显示成功或空详情。
- 返回大厅、直接访问、刷新、重试与金额分转元均可验收；真实写入、身份鉴权、报价和接单不属于本次 C 的完成范围。
